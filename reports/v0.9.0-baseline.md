  - Quick Convert implementation
  - Configuration management

#### Operations Registry (`opsRegistry.ts`)
- **Purpose:** Central catalog of all 479 operations
- **Size:** 83.7 KiB, 3208 lines
- **Key Features:**
  - Lazy loading via operation chunks
  - Stable hash-based chunk allocation
  - Production vs development path detection
  - Module-based grouping (15 categories)
  - Factory pattern for operation instantiation

#### Operation Chunk System
- **Configuration:** `operationChunkPlan.json` defines 15 modules with shard counts
- **Overrides:** `operationChunkOverrides.json` for manual chunk assignments
- **Result:** 72 lazy-loaded chunks containing 479 operations
- **Cache:** `operationChunkCache` prevents duplicate loading

### 2.7 Existing Security Measures

#### Message Validation (`pipelineProtocol.ts`)
- Maximum limits defined:
  - `MAX_STEPS = 512`
  - `MAX_ARGS_PER_STEP = 256`
  - `MAX_NAME_LENGTH = 200`
  - `MAX_DESCRIPTION_LENGTH = 8000`
  - `MAX_RAW_LENGTH = 256000`
  - `MAX_MANUAL_INPUT_LENGTH = 16MiB`
  - `MAX_VALUE_DEPTH = 12`
  - `MAX_VALUE_ITEMS = 100000`
  - `MAX_ARGUMENT_CHARACTERS = 4MiB`
  - `MAX_ARGUMENT_STRING_LENGTH = 1MiB`
- Type validation for all message fields
- Operation name validation against known registry
- Recursive value safety checking with budget tracking

#### Webview Security
- Pipeline Editor: Nonce CSP, no inline handlers
- Input sanitization via `escHtml` functions
- Safe HTML escaping in result displays

#### Storage Security
- Symlink rejection in workspace paths
- Atomic writes
- Restricted mode support
- Schema validation

#### Execution Safety
- Immutable document snapshots for replacements
- Live preview allowlist (deterministic operations only)
- Size limits on all inputs and outputs
- No network operations without explicit user action

## 11. Known Issues and Technical Risks

### 11.1 Current Issues (from Analysis)

| Issue | Location | Impact | Priority |
|-------|----------|--------|----------|

| Inline event handlers | Multiple webviews | Security | High |

| Marketplace description outdated | README/marketplace | Accuracy | Medium |
| 51 npm vulnerabilities | package-lock.json | Security | Medium |

### 11.2 Technical Risks for v0.9.0

1. **UI Refactoring Risk:** Modularizing webviews could break existing functionality if not thoroughly tested.

2. **Security Regression Risk:** Adding new security features might break existing valid workflows.

3. **Performance Risk:** Adding new features could impact startup time or memory usage.

4. **Compatibility Risk:** Changes to data formats could break saved pipelines/recipes.

5. **Test Coverage Risk:** UI modularization requires extensive new tests to maintain coverage.

### 11.3 Mitigation Strategies

1. **Incremental Changes:** Refactor one webview at a time with full test coverage.
2. **Feature Flags:** Consider feature flags for major UI changes (not implemented yet).
3. **Backward Compatibility:** Preserve all existing data formats and APIs.
4. **Extensive Testing:** Add integration tests before major changes.
5. **Performance Budget:** Maintain 3 MiB main bundle limit.
